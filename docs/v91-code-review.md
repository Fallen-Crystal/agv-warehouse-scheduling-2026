## 发现的具体缺陷

### P2：已回 Home 的车辆再次请求自身 Home，会重写真实最终到达时刻

位置：`src/agv/planning/reposition.py:26` 允许自身 Home；第47—49行无条件把该车最新任务的 `return_end/return_arrival` 改为新路径末时刻。若车辆已经回到 Home 并停留了若干步，这条合法的无位移请求会把历史到达时间延后。之后 `src/agv/evaluation/validation.py:299` 的独立检查会正确拒绝该结果。

已实际复现：单车、单任务、发布流结束200；任务返库在83完成，运行到85后调用 `env.reposition(0, home)`。API 接受并生成 `arrival=return_end=85`；最后完整运行被拒绝，错误为 `Final return time is later than actual home arrival`。

可复现代码：

```python
from agv.domain import Task
from agv.evaluation.validation import validate
from agv.simulation import Environment
from agv.warehouse.mixed import generate_current

s = generate_current(task_count=0, vehicles=1, order_stream_end=200)
row = next(r for r in s.map_info["rack_catalog"] if r["rack_type"] == "single")
s.tasks = [Task(0, None, s.stations[0], pickup_service=2, shelf=tuple(row["position"]))]
env = Environment(s.check(), positioning=True, router_kind="sipp")
env.assign([(0, 0)])
env.advance(env._records[0]["return_end"] + 2, observe=False)
env.reposition(0, s.homes[0])  # 接受，但不应延后先前已经完成的返库事件。
while not env.done:
    env.advance(observe=False)
validate(s, env.result())  # 当前冻结版本在这里抛出 ValueError。
```

这是公共动作接口的一致性缺陷。可在发布前明确拒绝这种 no-op，或者保留既有实际 Home 到达记录。当前注册 `PositioningPolicy` 在当前位置与自身 Home 相同且没有有效旧目标时不会发出这一请求；闭流后也不再定位，因此该反例不否定目前注册策略的已保存实验轨迹。发现问题后已通知主代理，冻结留出运行期间没有据此修改源码、删除场景或重选结果。本文记录的是 `ace242e` 状态，修复后应补充精确提交与回归证据。

## 本轮交互检查通过的范围

主代理随后实际通过本地浏览器操作G4（2车、4单动态），执行和返库完成；页面的通用算法摘要错误显示 `联合重规划调用 undefined 次`。原因是新策略也有 `algorithm` 字段，但没有旧联合重排的计数。该显示缺陷不影响路径、指标或正式实验，已与上述API边界一起在冻结测量结束后修复，并重新操作网页核查。

**因果信息边界。** 定位、ETA 匹配与 BCRD 的控制决策来自 `observe()`；没有调用离线 `lower_bounds`、评分参考或完整未来任务生成器。定位历史仅累积已经在 pending/active 中出现的任务。忙车未来卸货时刻来自已经提交的承诺路径，属于当前可见信息。实际环境的 stream end 由发布者控制；控制器看到的是事件已经发生后的 closed 标志，不会获得未来关闭时刻。

影子环境中 `len(_jobs)` 指重建后的可见任务集，不是实际订单流总数。开放流预测在当前已知任务完成时停止，既不虚构关闭事件，也不计未执行的最终返库；已经 closed 才完成全部返库。历史 `idle_waits`、待命计数、已完成耗时、旧返程记录均已恢复。非零时刻真实环境与影子环境连续5步完整观察及预约后缀的差分测试通过。未发现当前注册策略可触发的未来任务泄漏。

**重定位与预约。** `env.reposition` 检查 V9.1 显式 opt-in、未承诺任务、普通通行目标或自身 Home，并同时规划前往目标和安全返库后缀。所有检查发生在更新 routes、任务记录和定位事件之前；失败只可能消耗规划统计，不会提交部分路径。新订单可中断未承诺的定位移动；同一 tick 中尚未执行的旧定位事件会被删除，避免独立验解误读事件先后。

`PlanReservations` 只对真实路径替换重建空间索引；等待以绝对起点平移和当前停留区间覆盖表达。正反边、对方最终静止尾部、候选自身最终静止尾部都在冲突检查中。有效调用下，多步等待不会与尚未结束的同车等待重叠。O(1)描述的是索引等待维护，整个 `hold_return` 仍需构造后缀并检查其未来冲突。

**执行与计账。** 重定位路段没有服务订单，但实际移动继续计入 `moves/empty_moves` 和既有 `0.05D` 移动能耗代理。普通待命和交通等待分开记录；独立验解依据实际位置、任务服务区间、定位/等待事件重建统计，不直接信任区间状态标签。不可把“通过验解”解释为停车点最优、真实电池能耗准确，或长期拥堵不会发生。

**派单与尾部。** ETA 匹配使用同一 SIPP 规划规则作估计，真实提交仍由 `Environment.assign` 按序执行与检查。多个独立 ETA 组合后，实际规划结果可能因先提交车辆预约而变化，这属于启发式估计误差。延迟上限16限制的是本机制主动推迟行为，不保证任何订单在16步内必然获得可行路线。

BCRD 不接受定位状态或历史有限 TTL 待命的未验证组合。候选必须预测完整的当前已知工作量；预算失败、残余订单或基准预测失败会保留安全贪心。tail guard 使用相同已完成耗时历史与当前已知订单，拒绝预测 P90 高于贪心的候选。它没有对未知未来流量的实际 P90 提供硬保证。
