# BCRD：有序批次影子派单实验报告

**BCRD（Ordered-Batch Counterfactual Rollout Dispatch）** 在当前已发布订单池中构造少量合法的有序派单批次，借助真实 SIPP 规划器与影子执行环境进行反事实前瞻试算，再择优提交本步动作。该策略完全沿用既有路径规划器、货架层序规则、装卸时长与 V4 评分体系，且不撤销已承诺订单。

**核心结论**：
- 在 **90 个留出场景** 上，BCRD 将综合分数 `F` 平均改善 **0.406%**（95% 配对 bootstrap 区间 `[0.069%, 0.737%]`），主要收益来自静态积压订单（静态分层组平均改善 **1.166%**）。
- 引入保持轨迹完全一致的**事件驱动影子推进**后，同轮测量的 `CPU/G0` 从 **3.16 降至 1.77**（留出总 CPU 降低约 43.2%）。
- 在 **20 个尺寸与负载泛化场景** 上，平均 `F` 改善 **0.535%**，`CPU/G0` 为 **2.28**。
- 鉴于动态设备组置信区间跨零、动态共享 D 站组收益为零，且部分场景出现响应尾部（P90）退化，BCRD 保留为显式可选策略，维持既有默认配置。

阶段 A 逐单耗时诊断数据见 [`results/bcrd/diagnosis/`](../results/bcrd/diagnosis/)，开发集与正式实验的完整校验审计见 [`verification.json`](../results/bcrd/verification.json) 与 [`release-validation.json`](../results/bcrd/release-validation.json)。旧版 `results/v4/` 完整保留未改动。

## 1. 算法机制与在线前瞻设计

默认配置 `bcrd_budget` 使用 **最多 4 个候选批次、SIPP 后端、关闭联合重规划**。为避免低负载下的无效前瞻开销，仅当保底贪心批次可同时分派至少 2 辆车、且当前合法待派订单数至少为可用车数的 3 倍时才触发影子搜索；低压力时刻直接采用合法贪心，全过程仅依赖当前可见状态，严格隔离未来到达信息。

候选批次按确定顺序从**贪心、匹配、最老订单、长任务、受限资源与逆序**中生成，经去重后截断至上限 4 个；另设消融变体 `bcrd_order`，固定与保底贪心相同的车—单配对，仅调整预约提交顺序，用于隔离提交顺序耦合效应。

每个候选在影子环境中对**当前可见世界**执行一层当前动作试算，并在后续步骤统一采用合法贪心完成 rollout（聚焦当前可见积压，保持轻量与可解释性）。在线评分代理采用可见预计剩余完工时间、平均响应与未来移动量的 50/30/20 加权比值，其归一化分母固定为同决策时刻可见保底 rollout 的预测值，与离线参考分母严格隔离。

计算资源预算约束为：单次决策最多 480 次真实影子 `leg` 调用、120,000 次扩展量软上限（在单条 `leg` 边界检查）以及单次预览最多 2,400 仿真步。若保底预览失败或预算耗尽，则安全回退至当前已完整评估的最优动作或合法贪心；真实环境最终仍按原合同完成独立验解与预约提交。

在消融中也测试了限制后续 1/2 批次的截断深度变体（`G_limited1` / `G_limited2`）：在缺少可靠残余尾估计的前提下，遇到残余截断时预览结果主动拒绝并安全回退，用以验证预算截断的安全兜底机制。

## 2. 实验协议与数据纪律

所有实验协议在运行前预先冻结并保存在 [`examples/experiments/`](../examples/experiments/)：
- **开发集（种子 10–19）**：3 模板 × 10 种子 × 9 配置 = 270 次（数据见 [`results/bcrd/development/`](../results/bcrd/development/)）。依据开发集权衡选定“四候选上限 + 队列比例门槛 3”并冻结参数，此后不再针对留出集调参。
- **留出集（种子 30–59）**：原 3 类模板 × 30 种子 = 90 个未见场景 × 7 配置 = 630 次。
- **尺寸/负载泛化集（种子 60–69）**：中型静态（30 单 6 车）与中型突发五层（36 单 6 车）两类模板 × 10 种子 = 20 个未见场景 × 3 配置 = 60 次。

所有对照配置统一采用 SIPP 后端并关闭联合重规划：`G0` 为合法贪心基线，`G1` 为静态匹配，`G2` 为冻结后的 BCRD（`bcrd_budget`），并配以顺序、无门槛与有限深度消融。原 V4 时空 A* 贪心仅作为统一离线 `F` 分母。

首轮共执行 **960 次**运行（`90b98ef`）；完成影子事件推进优化后，在同种子上执行 **440 次**实现等价性与 CPU 复测（`ad5bce1`），累计 1,400 次执行均完整完成并通过独立验解（独立未见质量场景总计为 90 个留出 + 20 个泛化场景）。计时仅覆盖算法核心运行，参考预热与外层验解均在计时之外；统计口径同时汇报均值、配对胜负平、固定 4,000 次配对 bootstrap 区间、P90/最坏响应退化及 `CPU/G0`。

## 3. 留出与尺寸/负载泛化结果

下表汇报各配置相对 `G0` 的逐场景配对改善率均值（正值为改善）与配对 `CPU/G0` 均值；质量数据首次产出于 `90b98ef`，`CPU/G0` 取自同轮事件版 `ad5bce1`（等价审计确认两者所有质量指标完全一致）：

| 场景 | 配对数 | F 平均改善 | 95% 区间 | 胜/负/平 | CPU/G0 | P90 更差场景数 |
|---|---:|---:|---:|---:|---:|---:|
| 留出：静态分层 | 30 | 1.166% | [0.660%, 1.718%] | 19/0/11 | 3.05 | 10 |
| 留出：动态设备障碍 | 30 | 0.052% | [-0.754%, 0.832%] | 5/5/20 | 1.25 | 3 |
| 留出：动态共享 D 站 | 30 | 0.000% | [0.000%, 0.000%] | 0/0/30 | 1.00 | 0 |
| **留出合计** | **90** | **0.406%** | **[0.069%, 0.737%]** | **24/5/61** | **1.77** | **13** |
| 泛化：中型静态，30 单 6 车 | 10 | 0.988% | [0.196%, 2.025%] | 6/0/4 | 3.53 | 4 |
| 泛化：中型突发五层，36 单 6 车 | 10 | 0.082% | [0.000%, 0.245%] | 1/0/9 | 1.03 | 0 |
| **泛化合计** | **20** | **0.535%** | **[0.110%, 1.067%]** | **7/0/13** | **2.28** | **4** |

**分场景机制解读**：
- **静态积压收益明确，但伴随响应权衡**：在静态分层留出集中，平均完工时间 `T` 从 186.00 步降至 179.37 步，总里程 `D` 从 633.87 降至 625.80，而平均响应 `R` 由 89.91 升至 92.32 步。受 `F` 中 50% 完工权重驱动，策略倾向于优先消化长链路或瓶颈订单以压缩整体拖尾，代价是部分短单等待延长（留出集有 13/90 例 P90 变差、5/90 例最坏响应变差；泛化集分别为 4/20 与 1/20）。
- **低积压动态场景保持零开销回退**：动态共享 D 站的全部 720 次决策均因队列压力低于门槛而直接采用保底贪心，避免无谓搜索；动态设备场景仅触发 15 次搜索，在后续订单未知的情况下呈现 5 胜 5 负。
- **泛化范围**：当前泛化集验证了 3 层/5 层规则下更高车数与订单量（30–36 单、6 车）的表现，进一步向更大规模与更深层数拓展的实验见后续 V9 与 V9.1 报告。

原始明细与汇总保存在 [留出结果](../results/bcrd/event-holdout/) 与 [泛化结果](../results/bcrd/event-generalization/)，逐次候选评估日志存于 `diagnostics.jsonl`，精选完整轨迹固定取各模板首种子。

## 4. 消融实验与停止条件

下表来自首轮冻结留出集（`90b98ef`，逐步影子版，详见 [原始留出结果](../results/bcrd/holdout/)）：

| 策略 | F 平均改善 | 胜/负/平 | CPU/G0 | P90 更差场景数 |
|---|---:|---:|---:|---:|
| `G1` 静态成本匹配 | 0.051% | 33/22/35 | 1.17 | 19 |
| `G2` 四候选、队列比例三（冻结方案） | 0.406% | 24/5/61 | 3.17 | 13 |
| `G_order` 仅调整同配对预约提交顺序 | 0.011% | 2/0/88 | 2.71 | 0 |
| `G_ungated` 取消队列比例门槛 | 0.559% | 38/10/42 | 3.88 | 22 |
| `G_limited1` 后续最多一批 | 0.000% | 0/0/90 | 1.18 | 0 |
| `G_limited2` 后续最多两批 | 0.000% | 0/0/90 | 1.20 | 0 |

消融结论清晰呈现了各组件的作用：
- 仅调整预约提交顺序（`G_order`）在 2/90 场景产生正向耦合收益（平均 +0.011%），主要改善仍由批次组合本身贡献。
- 取消队列门槛（`G_ungated`）虽将平均 `F` 改善再提高约 0.153 个百分点，但 `CPU/G0` 升至 3.88 且 P90 退化例数由 13 增至 22，性价比显著下降。
- `G_limited1` 与 `G_limited2` 各有 61 次预览因 `depth_limited` 残余约束触发安全回退，验证了截断保护逻辑正常工作；后续若要引入浅层规划，需先构造可靠的残余尾估计。
- 首轮 `G2` 触发了预设的效率优化阈值（`CPU/G0 > 3` 且平均 `F` 改善 `< 0.5%`），因此团队优先落地了无损的事件驱动影子推进，在不改算法行为的前提下将计算开销削减近半。

## 5. 无损加速：事件驱动影子推进

在影子 rollout 过程中，存在两类无需调用派单策略的空闲区间：一是全车忙碌时，直到最早一单卸货完成前都不会产生空闲车辆；二是全部可见订单均已派完后，车队只需完成剩余轨迹与回库。事件驱动优化在这些确定区间内跳过空政策调用，并仍通过原 `advance(delta)` 完整记录逐步轨迹；一旦存在可用车与待派订单，或触及自定义策略/深度边界，则恢复逐步语义。真实在线环境仍保持逐步推进，正常感知新订单发布。

同轮 CPU 复测对比（macOS ARM64，Python 3.12.13 单次计时）：

| 同轮 CPU 复测分组 | 逐步版平均秒数 | 事件版平均秒数 | 配对加速比均值 | 逐步 CPU/G0 → 事件 CPU/G0 |
|---|---:|---:|---:|---:|
| 静态留出（30 场景） | 1.838 | 0.838 | 2.17 | 6.70 → 3.05 |
| 动态设备留出（30 场景） | 0.541 | 0.380 | 1.32 | 1.78 → 1.25 |
| 动态共享留出（30 场景） | 0.311 | 0.309 | 1.00 | 1.01 → 1.00 |
| **留出合计（90 场景）** | **0.897** | **0.509** | **1.50** | **3.16 → 1.77** |
| **泛化合计（20 场景）** | **3.595** | **2.039** | **1.52** | **4.08 → 2.28** |

留出集总体平均 CPU 减少约 **43.2%**（逐实例配对加速比均值为 **1.50×**），事件版最大单次决策耗时为留出 0.483 秒、泛化 1.593 秒。

独立的 [等价审计](../results/bcrd/event-equivalence.json) 逐项比对了旧→新 330 对 `G0/G1/G2`、新事件→新逐步 110 对 `G2` 以及 20 对完整轨迹：剔除计时与事件开关字段后，所有 `F/T/R/D`、P90、完成率、规划计数、路径、服务标签、任务归属与候选解释的差异均为 **0**，20 份精选轨迹全部通过独立验解。

## 6. 典型案例与双栏同步回放

[离线双栏回放](../results/bcrd/replay.html) 固定展示静态留出首种子 30，支持左右同步播放与时间轴拖动，直观对照真实轨迹与事后评分指标：

| 指标（seed 30） | G0（合法贪心） | G2（BCRD） |
|---|---:|---:|
| `T`：最后卸货时刻 | 207 | 190 |
| `R`：平均响应 | 96.278 | 102.778 |
| `D`：含回库总移动 | 690 | 718 |
| P90 响应 | 172 | 186 |
| 最坏响应 | 207 | 190 |
| 综合分数 `F` | 1.000000 | 0.987307 |

在时刻 0 可见 18 单时，`G2` 对贪心、匹配、最老订单与长任务四个批次分别试算，得到可见代理分数 `1.000000`、`0.999308`、`0.987307` 与 `1.082364`，从而选择最老订单批次。由于该静态场景在初始时刻已释放全部订单，可见 rollout 与完整未来一致；仅调整这一初始批次即让最终 `F` 下降 **1.269%**。按分项拆解：`T` 项贡献 `−0.041063`，`R` 项 `+0.020254`，`D` 项 `+0.008116`，合计 `−0.012693`。这一案例直观揭示了 BCRD 的核心权衡：通过尽早消除尾部拖尾换取更优的综合 `F`，同时部分订单等待时间与总移动步数有所上升。

## 7. 复现命令与工程验证

```bash
python -m pip install -e '.[dev]'
agv run --profile v4 --tasks 18 --vehicles 4 --algorithm bcrd_budget --output runs/bcrd.json
agv benchmark-bcrd --protocol examples/experiments/bcrd-event-holdout.json --output runs/bcrd-event-holdout
agv benchmark-bcrd --protocol examples/experiments/bcrd-event-generalization.json --output runs/bcrd-event-generalization
python scripts/verify_bcrd.py runs/bcrd-event-holdout
python scripts/verify_bcrd.py results/bcrd/holdout --revision 90b98ef
python scripts/verify_bcrd.py results/bcrd/event-holdout --revision ad5bce1
python scripts/verify_bcrd_event_equivalence.py --validate-traces
python scripts/verify_v4.py --source-revision 8551943
agv serve
```

说明：`benchmark-bcrd` 在 Git 可编辑安装环境下运行，以完整记录源码提交与文件哈希；复核历史归档时通过 `--revision` 指定对应快照。

**工程验证小结**：
- 全部 **160 项**单元与集成测试通过，覆盖影子搜索触发、未来订单置换不变性、资源锁、部分装卸、回库、各类预算上限与事件驱动差分。
- 5 个实验目录共 1,400 行记录已通过 [独立重算审计](../results/bcrd/verification.json)，完整核验矩阵规模、源码 Git 树、文件哈希、配对算术、bootstrap 区间及 74 份精选轨迹。
- 全程保持 `planning/`、`warehouse/` 与 `evaluation/objective.py` 稳定不变，核心无第三方依赖；安全约束继续由真实路径规划器与独立验解器保障。
