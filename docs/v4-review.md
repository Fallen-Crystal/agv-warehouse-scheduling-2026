# V4 业务规则集成审核与改进方向

本阶段将队友 `agv_modeling_integrated_v4` 中新增的仓库几何与业务规则，有选择地集成到现有模块化架构中。V4 的核心贡献在于完善立体货架与交付站建模，其本身沿用原版预约式时空 A* 与距离贪心派单，因此集成时保留了现有工程边界与 SIPP/联合修复框架，同时原样留存所有旧版源码与结果。

集成版本通过了全部 **113 项单元与集成测试** 以及 **54 次同规则配对运行**（逐次数据、源码哈希与精选轨迹保存在 [`results/v4/`](../results/v4/)）。实测表明，新规则能够稳定、无碰撞运行；而既有优化算法面向旧目标设计，在 V4 综合评分体系下的收益较小且存在场景分化，由此明确了下一阶段“先诊断、再对齐目标”的优化路线。

## 1. 规则差异梳理与集成决策

| V4 变更内容 | 集成后的模块位置 | 处理决策与设计意图 |
|---|---|---|
| 背靠背货架、独立上下面、面/货位/层标识、唯一外侧取货位 | `warehouse/layout.py`、`warehouse/rules.py`、`domain.py` | 完整接纳，消除双侧货架资源混淆，提供清晰可解释的货位编码 |
| 分层装货时长 `2×层数`；同面同货位最高已释放层优先 | `warehouse/rules.py`、`simulation.py`、`evaluation/validation.py` | 接纳为统一业务约束，在派单、执行与独立验解三处同步校验 |
| D 站专用于本订单卸货，禁止穿行、提前占位或卸后滞留 | `planning/astar.py`、`sipp.py`、`pickup.py`、独立验解器 | 完整接纳，A* 与 SIPP 保持一致的终点角色语义 |
| 1–10 辆车、五档地图尺寸、作业通道宽度、柱体与设备障碍 | `warehouse/layout.py`、CLI、`web/` | 完整接纳，保留精确障碍几何与输入边界检查 |
| 无固定截止时刻，按全部完成或停滞终止 | `domain.py`、在线驱动、`simulation.py` | CLI 支持 `horizon=None`，Web 端继续保持有限执行资源上限 |
| 归一化时间/响应/里程综合评分 `F` | `evaluation/objective.py` | 接纳为离线评估口径，参考分母可独立复核且严格隔离在线策略 |
| 原扁平源码与固定预约调度 | `planning/`、`dispatch/` | 保留完整基线行为用于对照，复用现有模块化架构与 SIPP 框架 |
| 原 Web 页面与文档 | `web/` 与本文档 | 融合有效控件与状态展示，延续既有安全限制并统一更新规则说明 |

注：V4 层序约束按**当前已释放订单**判定——高层订单尚未发布时低层可正常接单，后续发布的高层订单不会抢占已承诺低层；同一货架面在上一单装货结束后释放，背靠背的另一面相互独立。装货时长、目标权重与能耗系数均为课程建模设定。

## 2. 跨模块审核发现与关键修复

队友原版 71 项测试均已通过；在集成审核中，我们补充构造了跨模块边界反例，定位并修复了三类隐患：

| 审核发现的反例 | 修复措施 | 回归测试覆盖 |
|---|---|---|
| 输出记录省略可选 `shelf` 字段时，验解器可能漏查同面接单互斥，掩盖过早承诺 | 验解器改为按 `task_id` 从不可变场景输入恢复货架资源，严格审计接单时刻与层序 | `test_v4_execution.py` 缺失元数据反例 |
| `service_axis='any'` 与严格 D 站元数据混用时，序列化可能丢失规则与参考信息 | 显式区分 `legacy` 与 `v4` profile，拒绝混合或未知规则字段，保证合法输入无损往返 | `test_v4_domain.py` profile 与序列化测试 |
| 最早到达时刻卸货结束后唯一出口恰被占用时，原组合器直接判定无解，实际延迟一拍到达即可通行 | 为交付段增加最早到达约束；当出口受阻时最多尝试 8 次延迟到达（A* 与 SIPP 行为一致） | `test_v4_execution.py` 卸货后立即退出反例 |

其中第三项交付退出修复有效提升了严格 D 站下的路径可行性（设 8 次延迟重试上限以控制搜索开销），并同步应用于基线与所有候选策略，确保实验比较公平一致。此外，回归测试全面覆盖了未来订单隔离、同面批量接单原子拒绝、严格 D 站下的 A*/SIPP 差分、无截止与停滞终止、评分防篡改及 CLI/HTTP 入口。

## 3. 评价口径与配对实验设计

V4 综合评分 `F` 越低越好：

```text
F = 0.5 × T/Tref + 0.3 × R/Rref + 0.2 × D/Dref
T = 最后一个订单卸货完成时刻
R = 平均（卸货完成时刻 − 订单发布时间）
D = 全部执行移动步数（含卸货后回库）
```

说明：仿真最终结束时刻还包含最后一次回库，与 `T` 分别统计；`0.05×D` 仅作为能耗展示代理，不重复计入目标权重。综合评分仅在方案完整可行且同场景参考基线成功时有效，失败样本保留原始记录而不混入成功均值。

参考基线固定为**包含交付退出修复的分层距离贪心 + 预约时空 A***（无联合重规划，场景 profile 为 `math-v4-integrated`，评分实现标识为 `math-v4-reviewed-v1`）。所有离线参考分母与未来订单均严格与在线观测隔离。

正式实验涵盖 **3 类场景族 × 6 个种子（0–5）× 3 种策略 = 54 次**运行，全部完成并通过独立验解（V4 小尺寸、三层货架、无固定截止）：

| 场景族 | 订单与车辆 | 额外场景特征 |
|---|---|---|
| `static_layers` | 18 单、4 车 | 静态已知订单、分层装货 |
| `dynamic_equipment` | 24 单、6 车 | 动态突发到达、柱体与设备障碍 |
| `dynamic_shared` | 24 单、6 车 | 动态不规则到达、共享 D 站 |

对比策略包括：`baseline`（固定参考）、`sipp_budget`（SIPP + 拥堵关联候选，最多 6 次联合修复尝试）以及 `sipp_matching`（在 `sipp_budget` 基础上叠加当前批次最小代价匹配）。旧版学习排序模型基于历史规则训练，因此暂未纳入 V4 正式对照。计时前预先完成参考基线计算并按种子轮换算法顺序，以减少冷启动与顺序偏差；本组数据反映 6 种子小样本探索下各策略的相对表现。

## 4. 实测结果与权衡分析

下表为每类场景 6 个种子的均值；`F 改善` 为相对配对基线的分数下降百分比（正值代表改善，负值代表退化），时间与里程以离散步计量（逐次数据见 [`runs.csv`](../results/v4/runs.csv)，汇总见 [`summary.json`](../results/v4/summary.json)）：

| 场景 | 策略 | F | F 改善 | T | R | D | 运行秒 |
|---|---|---:|---:|---:|---:|---:|---:|
| 静态分层 | baseline | 1.00000 | 0 | 176.17 | 87.19 | 617.33 | 0.478 |
| 静态分层 | sipp_budget | 0.99922 | +0.078% | 176.00 | 87.14 | 617.00 | 0.913 |
| 静态分层 | sipp_matching | 1.00675 | −0.675% | 176.00 | 87.44 | 632.00 | 0.960 |
| 动态设备 | baseline | 1.00000 | 0 | 171.83 | 45.74 | 891.33 | 0.500 |
| 动态设备 | sipp_budget | 1.00660 | −0.660% | 173.00 | 45.85 | 903.00 | 1.129 |
| 动态设备 | sipp_matching | 1.00947 | −0.947% | 174.67 | 45.61 | 899.33 | 1.127 |
| 动态共享 D | baseline | 1.00000 | 0 | 220.83 | 57.53 | 1003.33 | 0.563 |
| 动态共享 D | sipp_budget | 0.99989 | +0.011% | 221.67 | 57.42 | 998.67 | 1.202 |
| 动态共享 D | sipp_matching | 0.99680 | +0.320% | 220.50 | 57.35 | 998.33 | 1.200 |

注：综合分数 `F` 先按单场景独立归一化再跨种子取平均，因此与用跨种子均值直接代入公式的结果略有差异。

从结果中可以总结出三个关键发现：
1. **局部优化目标与全局评分存在错位**：现有联合修复按“已接任务剩余送达时间之和、回库时刻、移动量”的字典序验收候选，而 V4 评价由 50% 完工时间 `T`、30% 平均响应 `R` 与 20% 总里程 `D` 加权构成。例如动态设备场景中 `sipp_matching` 虽略微降低了 `R`，却因改变后续接单时机导致 `T` 和 `D` 上升，最终拉高 `F`。
2. **平均响应与尾部体验存在权衡**：在动态共享 D 场景中，`sipp_matching` 的平均响应 `R` 改善了 0.314%，但 P90 尾部响应退化 3.571%；`sipp_budget` 的 P90 退化 5.893%。这说明后续优化必须同时监控 P90 等尾部公平性指标。
3. **固定服务与层序门槛压缩了路径重排空间**：两种 SIPP 修复策略的耗时约为基线的两倍，综合改善最高仅 0.32% 且在动态设备场景出现退化。这提示在 V4 规则下，与其盲目加大路径搜索预算，不如先做耗时分解与决策层对齐。

因此，在 V4 场景中推荐将 `baseline` 作为低开销参照，把两种 SIPP 策略保留为实验选项；历史旧规则下的 396 次实验结果继续独立归档，与 V4 各自保持清晰边界。

## 5. 后续优化路线图

结合上述诊断与调研资料中“先分解诊断、建立小规模同语义参考、再分阶段优化”的思路，梳理出面向 V4 的后续研究优先级（除“已实现”项外均为待开展的演进方向）：

| 优先级 | 研究内容与设计思路 | 验收与退出标准 |
|---|---|---|
| 已实现 | 集成 V4 分层与严格 D 站规则，修复验解/序列化并加入最多 8 次交付退出重试 | 全部跨模块反例与回归测试通过 |
| P0 | 逐单拆分待派、空驶、装货前等待、装货、载货、卸货前等待与卸货耗时，并记录门控与修复原因 | 各阶段加和精确等于订单耗时，明确固定服务与交通等待的主导关系 |
| P1 | 构建 2–4 车、少量订单的同规则小实例参考（区分固定派单与允许重派单） | 量化现有策略的真实可优化空间，区分超时与无解 |
| P2a | 将在线局部目标与 V4 的 T/R/D 权重对齐，使用可见订单增量与显式尺度构造代价 | 同预算消融，严格隔离未来信息，同时汇报 F、P90 与 CPU |
| P2b | 若 P1 显示跨段出口耦合显著，则探索取货—交付—退出联合搜索或带业务阶段的 SIPP | 优先验证最小反例，保持服务连续与 D 站不滞留 |
| P3 | 在层/面门控后，仅对高压力候选配对计算有限 SIPP ETA，并单独消融预约提交顺序 | 相同候选预算与公平回退，同时报告匹配数与尾部响应 |
| P4 | 按新单发布、服务完成或高冲突压力自适应触发重排，低压力时缩减预算 | 实际 CPU 耗时明显下降，且满足预设质量阈值 |
| P5 | 在规则支持合法待命/调位后，于独立新场景划分上再行探索学习排序 | 明确任务归属与返库合同，保持在线信息隔离 |

优先推进 **P0 + P1 + P2a** 是性价比最高的路线：先量化耗时组成与可优化余量，再针对已暴露的目标不一致问题验证决策层对齐的边际收益。

## 6. 复现与验证命令

在项目根目录完成可编辑安装后运行（输出目录需为新路径）：

```bash
python -m pip install -e '.[dev]'
python -m unittest discover -s tests -t . -v
ruff check src tests
ruff format --check src tests
agv run --profile v4 --mode dynamic --vehicles 10 --layers 3 \
  --obstacles columns_equipment --tasks 24 --algorithm baseline \
  --output runs/v4-baseline.json
agv run --input runs/v4-baseline.json --algorithm sipp_budget \
  --output runs/v4-sipp.json
agv benchmark-v4 --seeds 6 --output runs/v4-reproduction
python scripts/verify_v4.py
python scripts/verify_results.py
agv serve
```

其中 `--input` 会复用完整场景定义并重新运行指定策略；Web 端导入支持最大 96×96、10 车、60 单、1800 步（无截止长场景通过 CLI 执行）。`verify_v4.py` 可独立重建全部 54 行指标关系、配对摘要与同场景参考并验解 6 条完整轨迹，审核清单见 [`review-validation.json`](../results/v4/review-validation.json)，Web 示例场景见 [`v4_small_dynamic.json`](../examples/scenarios/v4_small_dynamic.json)。另外已在源码目录外安装 `0.3.0` wheel，实测 10 车 V4 SIPP 运行与打包页面资源均正常。
