# 第二轮审核落实与跨日期验证

本轮落实第二轮审核中能独立验收的兼容层清理、仓库卫生、日期评估、热点优化、退化诊断和组合实验。生产源码冻结于 `6daa04c`，新协议先以 `f6cd41e` 提交，开发选型以 `9c2b21a` 提交后才启动验证。后续提交只增加测试、离线工具、文档和证据，没有改策略参数或执行规则。

## 结果与采用决定

**保留 gate 默认。** 预约查询与待命推进的工程优化保留；`gate_anchor_tail` 作为有验解和实验记录的可选组合。开发集选择组合方案，并不意味着它达到了默认采用门槛。验证的日期区间跨过零，CPU 增量超过 10%，且存在窗口退化，三项均不支持切换。

| 方法 | 开发按日期平均 F 改善 | 验证按日期平均 F 改善 | 验证日期 bootstrap 95% | 验证改善/退化/持平日期 | 验证平均 CPU 秒 |
|---|---:|---:|---|---|---:|
| gate | 0 | 0 | [0, 0] | 0/0/10 | 27.905 |
| gate_anchor | −0.008% | +0.167% | [−0.396%, +0.708%] | 5/2/3 | 32.197 |
| gate_anchor_tail | +0.263% | +0.227% | [−0.207%, +0.750%] | 5/3/2 | 32.161 |

验证 anchor 的双侧精确符号检验 p=0.453，组合方案 p=0.727；均未提供稳定改善的证据。CPU 分别比 gate 增加约 15.38% 和 15.25%。这些是同机并行批次的进程 CPU 描述，不能当作跨硬件性能保证。

选型使用预先固定的“每个日期先平均原始 F，再对日期等权平均；CPU 打破相等”规则。表中的平均百分比是另一种效果描述，分母不同，不用于反向修改排名。开发原始日期均值分别为 gate 1.323207、anchor 1.321832、组合 1.319273，因此选择组合；没有根据验证结果重新选算法。

## 日期与输入边界

原协议的 8 个封存窗口及其 5 个日期继续保护。新筛选放宽到完整 900 秒窗、20–100 单、SKU 1–8，仍要求两种作业各至少 5 单、前缀库存非负且合计不超过 900、末库存非负、合成仓库容量可行。库存前缀仍使用全部源记录，排除窗口不会跳过库存更新。

排除旧原协议和第一轮协议共 40 个窗口标识后，有 51 个可行窗口，覆盖 26 个日期。先按日期采样，每日期最多两个窗口，得到：

| 集合 | 日期数 | 窗口数 | 算法运行数 |
|---|---:|---:|---:|
| 开发 | 6 | 11 | 33（3 方法） |
| 验证 | 10 | 15 | 45（gate、固定 anchor 对照、开发选出的组合） |
| 新封存 | 6 | 7 | 0 |

验证和新封存日期不出现在已知做过算法研究的日期集合中；开发允许使用已有研究日期。这里“已知”由仓库的历史协议记录定义，并非对任何人从未看过这些日期的证明。原始数据源与合成几何仍相同，不能声称跨仓库、跨来源或真实工厂泛化。

日期是主要统计单位：先计算同日期各窗口的配对百分比，再日期等权，使用固定种子的 4000 次日期 bootstrap；精确双侧二项符号检验排除平局。窗口和随机种子不会增加独立日期数。10 个日期比之前的 3 个更多，但仍是小样本。

放宽分布没有替换原筛选条件。新验证集中满足旧 30–80 单、SKU 2–6 条件的子集有 **7 个窗口、6 个日期**：anchor 平均改善 +0.470%，区间 [−0.056%, +1.169%]；组合 +0.479%，区间 [−0.058%, +1.167%]。子集同样没有排除零。旧报告的 +0.492% 属于旧窗口和旧统计口径，不能与新全集直接相减判断算法变强或变弱。

## 保持行为的热点优化

两份旧开发窗口的 cProfile 显示，SIPP 占总时间约 52–62%，idle hold 约 26–33%，GA 候选生成不足 1%，快照约 0.002 秒。这里是包含子调用的累计时间，不能把各项简单相加。

对应改动只有三类：

1. 从有限预约的路线端点直接求规划时域上界，避免枚举每一个预约时刻。
2. 在同一预约表版本内缓存不可变边索引；路线替换或 hold 会使索引失效。一个 trip 的多段 SIPP 查询复用同一索引，反向边冲突判断保持原义。
3. 同一时刻检查多辆待命车时只构建一张预约表，每次成功 hold 立即更新该表，供后续车辆观察。

四对原提交 `1b36902` / 新源码的独立进程对照，完整 JSON 语义哈希一致，仅排除 `row.cpu/wall`。路径、标签、任务分配、服务记录、搜索日志、路由计数、库存和评分全部相同。8 次运行均独立验解有效。

| 旧开发窗口 / 方法 | 原 CPU 秒 | 新 CPU 秒 | CPU 减少 |
|---|---:|---:|---:|
| day40-bin3870 / gate | 20.681 | 16.755 | 18.99% |
| day40-bin3870 / anchor | 28.182 | 29.110 | −3.29% |
| day38-bin3704 / gate | 32.976 | 23.730 | 28.04% |
| day38-bin3704 / anchor | 47.943 | 34.477 | 28.09% |
| 合计 | 129.782 | 104.072 | 19.81% |

单对仅一次，且同机存在其他 Python 批次，不构成至少下降 30% 的验收证书。cProfile 的 28–30% 降幅受剖析开销影响，没有拿来替代正常运行计时。

没有采用“车—订单分配相同就跳过动态匈牙利预演”或“只模拟一辆受影响的车”：动态匹配会随货位、完成事件和预约更新重新决策，固定 owner/order 并不等价；交通冲突也会传播到其他车。两窗 anchor 完整尝试分别 10 和 13 次，其中完整完成 2/0 次，其余被原界剪枝；跳过、局部预演均为 0。此次加速来自预约查询，不是 EtaCache 命中，也没有减少原搜索预算。

## 组合效果与退化原因

`gate_anchor_tail` 只组合既有第二锚点与公开闭流后的 tail 标志；保持原 GA 主流程、额外预演上限和真实 F 严格改善才接受的规则。它在验证中按日期平均 T 下降 4.15 步、R 增加 0.051、D 下降 4.4、P90 下降 2.45；收益主要来自 T，响应没有同步改善。线性 F 分项变化为 T −0.002306、R +0.000017、D −0.000163，合计 −0.002451。

旧 3 个开发退化窗口、2 个验证退化窗口的首次预测、派单、物理分叉已分别提取，并绘制双栏轨迹图，见[逐窗诊断](anchor-regressions.md)。五例首次预测分叉都发生在仍有未发布任务时，预测分数严格改善，没有平局证据。日志中的可见任务 SIPP 预测与最终整窗目标的差，不能证明 GA 代理评分错误；目前归类为“与滚动决策连锁效应一致”，尚未做因果候选互换实验。

因此不据此启动代理学习或宣称修复了所有回退。只在闭流后启用 anchor 可作为以后独立开发假设；本轮未在看到验证结果后添加或调试该策略。

## 实测延迟补充

本机为 **Apple M5 / Mac17,4，Python 3.12.13，macOS（完整系统标识见计划）**。测量计划在任何补充运行前提交；固定 `scale=1`，每次决策 CPU 秒向上取整为仿真步，单个 solver 进程串行，无结果缓存。三方法各跑 15 个验证窗口的 measured 模式，另跑 15 次 Hungarian none；gate/anchor 的 none 对照复用已重新验解的 30 次主验证，共新增 60 次运行全部有效。

| 方法 | 不计延迟 F（日期等权） | 计实测延迟 F（日期等权） | 计延迟时平均 CPU 秒（日期等权） | 相对匈牙利平均改善：none → measured |
|---|---:|---:|---:|---:|
| gate | 1.018545 | 1.019184 | 22.383 | 2.072% → 2.154% |
| gate_anchor | 1.016703 | 1.023830 | 25.360 | 2.253% → 1.544% |
| hungarian | 1.039114 | 1.041876 | 1.036 | 0.000% → 0.000% |

gate 的相对优势从 2.072% 到 2.154%，没有在这台机器上明显缩小；不能按原先预期写成“必然被匈牙利反超”。额外锚点相对匈牙利的优势从 2.253% 降到 1.544%。便宜的匈牙利方案仍有很大的计算成本优势：measured 的日期等权 CPU 约 1.036 秒，gate 约 22.383 秒。这里只是一个机器、一个种子的补充取舍，不参与默认选型。

延迟也改变了后续车辆位置、可见订单和预约，因此 T 或 F 的变化不必逐项单调变差。此模型记录“可见状态复制＋策略决策”的 CPU，提交前会重新规划检查；它没有覆盖整个系统的构图、仿真和验解耗时。离散向上取整使轻量决策也可能花 1 步，尤其影响匈牙利方案，不能把该口径直接等同于连续时间生产系统。none 的 GA CPU 来自主验证并行批次，measured 来自串行批次，两列 CPU 不用于证明延迟模型本身提速。

当前分支包含补充工具；在源码与新协议匹配的 checkout 中生成自己的机器计划，避免直接重用 M5 计时身份：

```bash
python scripts/benchmark_wepa_latency.py prepare --protocol runs/latency/protocol.json --plan runs/latency/plan.json
python scripts/benchmark_wepa_latency.py run --protocol runs/latency/protocol.json --plan runs/latency/plan.json --output runs/latency/results
```

本轮算法种子固定为 0，没有测试多种随机种子、其他几何或其他数据源；这些补充结果不提供跨机器或全局最优保证。
