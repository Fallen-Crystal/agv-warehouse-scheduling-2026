# 仓库 AGV 在线联合重规划：论文调研与算法选择

调研日期：2026-10-14。本文区分原论文的结论、本项目的适配判断与需要实验验证的效果；只引用论文原文、作者页面及正式出版方。性能数据以项目配对实验的实际输出为准，不把论文的大规模实验结果当成本项目结果。

## 1. 现有程序的问题对应什么研究方向

当前问题是在线多智能体取送任务（MAPD）：订单逐步发布，一辆 AGV 要依次到货架的合法相邻取货格、完成装货、到送货格、完成卸货，并返回专属停车位。车辆共享道路，需要检查同一时刻占据同一格的顶点冲突，以及同时沿同一边反向行驶的对向交换冲突。

原项目 `Environment.assign()` 在接单时调用 `plan_task()`，按给定车辆顺序生成取货、送货、返回整条路线；`Router.leg()` 用含等待动作的时空 A* 避开已经预约的路线。车辆接单后，`advance()` 逐步执行既定计划。这个机制能处理已有预约，却没有同时撤销并重建多辆忙车未来路线的接口。因此后接单车辆承担先接单车辆留下的绕路和等待，即使换一种通行顺序能让整个车队更快，也无法重新协商。这是对本地源码的判断。

MAPD 的经典定义和本项目的“在线发布、先取后送”直接对应；Ma 等人的 TP/TPTS 针对这一问题，并在满足特定结构条件的 well-formed 实例上给出完成保证。本项目尚未证明地图满足那些条件，不能直接继承其保证。见 [Ma 等，AAMAS 2017，作者论文原文](https://jiaoyangli.me/files/2017-AAMAS.pdf)、[作者所属研究机构的论文记录](https://publications.ri.cmu.edu/lifelong-multi-agent-path-finding-for-online-pickup-and-delivery-tasks)。

## 3. 推荐的融合方案及准确命名

实际实现选择 **RHCR 思想启发的在线联合后缀重规划，结合 MAPF-LNS 的可行解改善机制，使用优先级规划与现有时空 A* 修复路线**。代码对应 `joint_planning.py`、`optimized.py` 与 `Environment.apply_replan()`。

这是经典方法的工程适配，不是新发明 RHCR、LNS 或 A*，也不是完整复现其中任一论文。

RHCR 原文有窗口长度 `w` 与重规划间隔 `h`，要求 `h <= w`，只检查前 `w` 步冲突，执行前 `h` 步后再重规划。本实现默认每 5 步或新任务成功指派后尝试重规划，继续检查每辆车完整的剩余取送返回路线，让现有环境始终持有可执行的备选计划；它继承了滚动决策思想，但不应标为论文原版有限窗口 RHCR。见 [RHCR 原文，第 4 节](https://jiaoyangli.me/files/2021-AAAI-2.pdf)。

MAPF-LNS 的依据是：保留当前可行解，联合修改车辆子集，其他路线作为固定约束，接受目标改善的候选。原论文还有基于延误、地图交叉点与随机选择的邻域及自适应选择，本项目若没有实现这些机制，不应宣称完整实现 MAPF-LNS。见 [MAPF-LNS 原文，第 4–6 节](https://www.ijcai.org/proceedings/2021/0568.pdf)。

### 3.1 冻结过去，只优化真实可修改的未来

在仿真时刻 `t`，车辆实际已经执行的轨迹前缀不可改变。取货、送货的任务归属也不可改变；算法优化行驶路线和未来通行顺序，避免通过“取消正在执行的订单”制造虚假收益。

需要根据当前阶段构造剩余目标：

| 当前状态 | 需要保留的事实 | 可以重规划的内容 |
|---|---|---|
| 去取货 | 已分配订单、当前车位 | 未来取货路径、尚未开始的停靠点选择、随后送货及返回 |
| 正在装货 | 当前停靠格、原装货开始时间、已执行服务量 | 冻结余下装货占位，服务完成后的送货及返回 |
| 去送货 | 已装货事实、原取货记录 | 未来送货及返回 |
| 正在卸货 | 当前送货格、已执行服务量 | 冻结余下卸货占位，服务完成后的返回 |
| 正在返回 | 已完成送货记录 | 剩余回程 |
| 停车空闲 | 当前专属停车位 | 在没有新任务时原地保持 |

服务时间必须连续完成；不能把已经装到一半的货物恢复成未装货，也不能提前改写服务完成时刻。`repair_vehicle()` 保留已开始服务的时间记录，并将剩余服务表示为原地等待片段。如果先修复车辆的路线占用了后修复车辆的冻结服务位置，后者修复失败，该候选不会提交；完整候选还需要环境独立验收。这种实现可能错过一些可行候选，但不会为了新路线中断服务。

### 3.2 联合修复为什么能改善固定预约

对于一个选中的车辆集合，暂时删除其可修改未来的预约，保留固定车辆的预约与所有冻结片段。按多种车辆优先顺序重新调用时空 A*，每成功规划一辆就加入新的顶点、边预约。再对完整候选统一检查碰撞、障碍物、任务顺序、服务持续时间及返回停车位。

“联合”指多辆车的未来路径一起进入候选并一起提交；低层仍逐车搜索，不是在所有车辆坐标的笛卡尔积上做联合 A*。如果只给最后一辆车重找路，而其他忙车未来路线一直不可修改，就仍然是原来的限制。

`JointPlanner` 对仍有剩余路线的车辆生成循环轮换顺序及其反序，默认最多取 8 个全车队候选；若上述顺序不足，再用以当前仿真时刻为种子的随机排列补足。随后尝试车辆 ID 顺序中相邻两车的局部邻域，固定其他车辆路线。它没有实现延误启发式、自适应邻域权重或所有排列枚举。若一次全部撤销后无法修复，保持原计划；不能留下“部分车辆已经换路，部分还没成功”的混合状态。

### 3.3 目标函数与改善接受

实现使用如下字典序目标，先比较第一项，相等才比较后一项：

```text
(sum(max(0, delivery_end - now)),
 max(now + len(vehicle_suffix) - 1),
 sum(remaining_move_actions))
```

第一项遍历每辆车当前路线对应的任务记录，已送达任务贡献 0；第二项是车队剩余路线的最晚结束时刻；第三项只统计移动，不把等待当作距离。对于同一时刻、同一批固定任务，第一项的差等于这批未送达任务预计总流动时间的差。

只在候选完整可行且目标严格更好时统一替换未来路线，并记录提交时刻、涉及车辆、修改前后预计完成时间和路线变化。候选无解、预算耗尽、只有相同分数或分数更差时继续原方案。

实际日志 `replanning_events` 记录提交时刻、修改前后目标、候选数量，以及每辆改变路线车辆的执行状态、任务 ID、原/新送达时间和原/新后缀。它目前不保存最终采用的优先级顺序，因此不能从日志直接宣称某种优先级排序贡献了收益。

`Environment.apply_replan()` 在副本中安装候选，并再用独立审计副本执行完整剩余路线；该副本不指派新任务，使用 `validate()` 对实际历史与候选未来的服务顺序、碰撞和指标进行统一核验。环境还重新计算真实前后目标，要求与日志一致且严格改善，构造日志后再提交。真实已经执行的轨迹与区间状态标签不被候选覆盖。

### 3.4 与路径协商独立的可见订单匹配

`matching_action()` 只读取当前已发布待分配订单和空闲/返程车辆。对每个车辆—订单对，使用忽略动态冲突的静态距离计算：

```text
min_over_pickup_candidates(distance(current_position, pickup)
                         + distance(pickup, delivery))
+ pickup_service + delivery_service - 0.25 * visible_order_age
```

用车辆位掩码动态规划找最大匹配数量，再在该数量下找最小成本。默认模型最多 8 辆车，对这个可见订单成本矩阵的解是精确的；成本不含未来订单、动态预约等待及回程，因此不是实际车队全局调度最优解。订单年龄权重 0.25 是本项目参数，作用是让已经等待的订单更有机会被选中；仍不能据此证明所有负载下都无饥饿。任务分配的改进需与路径协商分别做消融评估。

这只能保证**这一轮同一批固定任务的预计局部目标没有变差**。重规划会改变车辆之后接到新任务的时间和位置，因此最终所有订单的流动时间、总移动量或 makespan 是否改善，仍要用相同订单序列的完整仿真实验判断，不能从局部接受条件直接推出。

## 4. 优化效果的可解释性

该方案的因果假设是：固定接单优先级把窄门通行资源长期锁给先规划车辆；允许两辆或多辆忙车同时修改未来后，短任务或拥堵方向可以先通过，另一辆只需较短等待或小幅绕行，从而减少总等待和送达时间。这是本项目的设计推断，必须用轨迹与指标检验。

例如，原计划让 A 先过门、B 等 8 步；候选让 B 先过门、A 等 2 步。如果候选还保持所有服务约束、没有顶点或对向交换冲突，并且整体预计送达成本下降，这轮修改才有理由接受。这里的数字只是机制示例，不是实验结果。

解释具体收益时，应同时报告：

- 哪辆车何时正在执行任务，重规划在何时发生，改变了哪段未来路径。
- 窄门通过先后次序和等待位置是否改变，交通等待总量是否减少。
- 送达流动时间、全部送达 makespan、移动量及计算耗时的配对变化。
- 成功率、未完成任务、规划失败和碰撞检查结果。失败实例单独报告，不能把未完成订单排除后用更小的平均值冒充改善。

推荐消融保持同一个任务分配器和相同订单：仅原预约；仅改善任务分配；原分配加联合重规划；分配与重规划同时启用。否则无法辨别收益主要来自任务分配还是路径协商。

## 5. 为什么仍不保证全局最优

优先级规划的固定或有限个顺序不能穷尽所有协调路线，存在可解实例找不到解的情况；多次尝试只是增加候选机会。CA* 的快速实现适合当前课程项目，却没有全局最优或完备性保证。见 [Silver，2005](https://ojs.aaai.org/index.php/AIIDE/article/view/18726)、[RHCR 原文对 CA* 的讨论](https://jiaoyangli.me/files/2021-AAAI-2.pdf)。

此外，现有低层分别求取货、送货、回程并拼接，最早到达一个中间目标不一定给出最短完整多目标路线；预约会在各段之间引入时间依赖。RHCR 原文专门使用增加目标序号的多标签 A* 处理这一点。本项目若继续使用逐段修复，应把这一限制保留在报告中，而不能因为每段叫 A* 就宣称整条路线最优。见 [RHCR 原文，第 4.1 节及脚注 3](https://jiaoyangli.me/files/2021-AAAI-2.pdf)。

有限搜索预算、只使用已发布订单、保持已分配订单所有权，也共同限制了可搜索方案。CBS 的标准最优结论依赖其原问题、完整搜索和正确低层求解；将搜索截断、改为服务多目标在线任务后，不能自动借用该结论。见 [CBS 期刊论文](https://doi.org/10.1016/j.artint.2014.11.006)。

本项目适合表述为：**解决“途中不能联合修改多车未来路线”的接口与算法限制，在有计算预算和完整可行性验证的前提下搜索更好的可行计划；实际收益由配对实验支持，不保证全局最优。**

## 6. 本项目适配工作的贡献边界

可以归属于本项目的实现工作包括：把联合后缀重规划接入现有执行环境；根据取货、装货、送货、卸货、返回阶段保留不可逆状态；维护服务时间与新路线的一致记录；原计划回退和全车队原子提交；重规划事件日志；固定订单的对照实验和可解释轨迹。

论文贡献是 CA*/WHCA*、RHCR 框架、MAPF-LNS 和 MAPF-LNS2，必须明确引用。当前改造属于有针对性的融合与实现，不应写为“提出了新的全局最优多 AGV 算法”，也不应引用论文中数百、上千车规模的性能来证明本程序具备同样规模能力。
