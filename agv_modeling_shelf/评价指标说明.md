# 第三项改进：结果评价与分析

本项增加评价指标，不改变任务分配、路径规划、地图或车辆运动规则。默认样例的任务完成时刻和轨迹应与第二版一致。页面下方展示整次模拟结果，不随着动画时刻变化；这些数据用于事后分析，不能交给在线算法获取未来信息。

## 1. 订单响应时间

对任务j，释放时间为r_j，卸货完成时间为C_j，响应时间F_j=C_j−r_j。它包括任务出现后等派单、车辆赶往取货点、装卸及载货运输。

| 字段 | 页面名称 | 计算及解释 |
|---|---|---|
| mean_flow_time | 平均响应时间 | 已完成订单F的平均值 |
| max_flow_time | 最长响应时间 | 已完成订单F的最大值，检查是否有某单严重拖延 |
| p90_flow_time | 90%分位响应时间 | 将n个F升序排列，取第ceil(0.9n)项，至少90%的样本不超过此值 |
| response_sample_count | 响应样本数量 | 有多少单真正完成了卸货 |
| completion_rate | 完成率 | 已完成订单/全部输入订单；空任务集约定为1 |

P90使用nearest-rank离散分位数，不使用插值。12单时取升序第11项；1单时就是该单响应时间。样本少时P90可能接近最大值，不能据此声称充分测量了大规模系统的尾部性能。仅代表本次任务集，不是总体分布的概率保证。

页面和中文CSV将该项显示为“90%订单的耗时上限”：本次已完成订单中至少90%从出现到完成的耗时不超过此值。程序字段仍为p90_flow_time，报告中可注明统计名称为90%分位响应时间。它不是对未来订单的承诺，也不是全部订单的最迟完成时刻。

没有已完成订单但输入非空时，新增的最大值、P90及时间分解均值返回null，页面显示“—”，不显示为表现良好的0。旧字段mean_flow_time在这个情况下保留0以兼容以前接口，必须同时读取response_sample_count。空任务集约定响应类指标为0。

## 2. 时间花在哪里

对每个已完成任务：

```text
响应时间
  = 等派单时间
  + 前往取货时间
  + 载货运输时间
  + 装载和卸载服务时间
```

等派单=S−r；前往取货=P−S；载货运输=D−pickup_end；装卸时间为两个service之和。这里S是成功指派时间，P、D分别为开始装载、卸载的时刻。

前往取货、载货运输的时长包含各自路上的等待，因此不等于行驶格数，也不能把它们全部称为拥堵时间。平均分解满足mean_flow_time等于四个分段均值之和（有已完成订单时）。

对应字段为mean_dispatch_wait、mean_pickup_duration、mean_loaded_duration、mean_service_duration。每单明细task_metrics只保存真正完成的订单，不统计尚未执行的预约完成时间。

## 3. 空驶与载货距离

| 字段 | 含义 |
|---|---|
| moves | 实际发生的移动次数，包括最终返回停车位 |
| loaded_moves | 装载完成后到卸载完成前的实际移动次数；服务期间不移动 |
| empty_moves | 其他实际移动次数，含前往取货及返回停车位 |

每次上下左右移动1格记为1，原地等待不计距离。恒有moves=empty_moves+loaded_moves。本版这些值是网格边数，不是真实米数，也不能直接等同于能耗。

失败或中途停止时，只统计截至实际停止时刻执行过的移动；不统计尚未执行的返程或后续任务路径。

## 4. 每辆车的工作量

per_vehicle包含：车号vehicle、成功指派任务数assigned_tasks、已完成任务数completed_tasks、移动/空驶/载货格数，以及服务、空闲、行驶阶段等待步数。

task_busy_steps表示从任务成功指派到卸货完成的实际执行步数，包含执行途中等待和装卸。未完成任务只统计截止时刻之前已经执行的部分。它不包括卸货后的空闲返程。

task_utilization=task_busy_steps/time。分母time为所有车共用的实际模拟停止时刻，包含最终返回；time=0时约定为0。因此利用率较低可能是任务少、等待新订单或其他车辆最后返回较晚，不一定是算法差。任务利用率不能解释为“车辆运动时间占比”。

总体workload_cv为各车task_busy_steps的总体标准差除以均值，均值为0时约定为0。CV越小表示这一个工作量口径越均衡，但均衡并非主目标：为了让每辆车都忙而增加绕路，可能反而降低整体效率。

页面和中文CSV采用直白名称：“途中等待总步数”对应traffic_wait_steps；“车辆工作量差异”对应workload_cv。后一项仍是无量纲的变异系数，0代表各车一样忙，越大越不均衡，不是相差多少单或多少步。每车表的“途中等待步数”只统计该车。

每辆车还满足：移动+服务停留+停车空闲+行驶阶段等待=time。全部车相加等于车辆数×time。

## 5. 成功与失败必须分开

comparison_valid仅在feasible=True时为True，即所有任务完成且全部车辆已返回专属停车位。这是当前模型对完整场景比较的成功要求。

metrics_scope为all_tasks表示所有订单完成；为completed_tasks_only表示仅有完成子集。全部订单卸货完成但最后返回尚未结束时，metrics_scope可以是all_tasks，但comparison_valid仍为False。页面会明确提示。

失败场景的响应指标是诊断信息，不能直接与成功场景比较，也不能只平均成功样本而隐去失败次数。正式算法对比应先报告成功率及完成率，再报告统一场景中的响应和距离。具体失败惩罚如有需要，应另行规定，不能临时为某算法调整。

## 6. 在哪里看和导出

运行show_warehouse.py后，生成一个场景，地图下方有“本次运行结果”和“每辆车的工作量”。可下载汇总、每车、每单三个CSV；页面CSV使用中文表头，汇总保留场景参数及成功/统计范围标记，便于追溯。下载的是当前已生成场景，不是尚未应用的控件设置。

运行run_examples.py或run_dynamic_examples.py生成样例时，也会输出summary.csv和每场景的*_vehicles.csv、*_tasks.csv。这些Python输出用英文程序字段名，便于算法同学批量读取；本说明给出了对应解释。CSV用UTF-8带BOM，可用Excel打开。

## 7. 验证与报告分析

独立验证器根据实际位置与任务事件重建载货区间、服务区间及忙碌时段，不调用运行时metrics.summarize或读取其状态标签来计算新指标。它会拒绝P90、最长响应、空驶/载货、每车工作量、时间分解等被篡改的结果。

新增7项指标检查，包括人工可复算的小地图、主动延迟指派、离散P90、未完成任务、卸货完成但返程未结束、空任务、闲置车辆和故意篡改。另增加页面结果表和CSV入口检查。合计33个测试方法。

报告可回答：平均响应变快时，最慢的一单是否也改善？空驶是否减少？长时间等派单还是路上运输占主导？负载是否集中在一两辆车？这些都需要在同一个任务集、种子及地图上比较策略，不能只凭指标的存在声称算法更优。
