# 算法同学接入说明

本文件夹为货架任选侧版本。新任务使用shelf目标货架坐标，pickup为None；不能沿用tuple(j['pickup'])读取新任务。用Scenario.pickup_candidates或从地图四邻接位置取得候选，再用同一个候选计算取货和交付两段成本。assign仍提交车辆/任务对，参考规划器自动选侧；反馈和事件的pickup_point记录实际停靠位置。同一货架格的不同合法侧可同时装货，仍保留车辆避碰；大仓库为四列货架，详见《货架取货改动说明.md》。以下基本调用方式保持不变。

## 最小调用

在本目录运行 Python，替换 policy 即可。仅需标准库。

```python
from model import example
from environment import Environment
from baseline import greedy_action
from validation import validate

scenario = example(mode='dynamic', layout='bottleneck', seed=0)
env = Environment(scenario)
while not env.done and env.time < scenario.horizon:
    observation = env.observe()
    pairs = greedy_action(observation)  # 替换为你自己的策略
    feedback = env.assign(pairs)
    env.advance(1)
result = env.result()
validate(scenario, result)
```

完整 scenario 属于评测驱动；在线 policy 只接收 observation。不要把 scenario 或 env 传给在线策略来读取 _scenario、_jobs 等内部字段。当前为接口层隔离，不是阻止恶意读取的安全沙箱。

## 输入字段

observe() 返回独立深拷贝，修改它不会改变环境：

| 字段 | 含义 |
|---|---|
| time / horizon | 当前时刻及运行时限 |
| map | 宽高、障碍、货架及停车位；坐标为 (x,y)，从0开始 |
| vehicles | id、position、state、available、task_id |
| committed_path | 正在执行任务的整段既定路线，从当前时刻开始，含返程 |
| return_path | 当前可接单车辆的返回计划，从当前时刻开始；可以被新任务替换 |
| pending | 已释放且未指派的任务：id、pickup、delivery、release、两个service |
| completed | 已卸货完成任务的实际事件时间 |

available=True 包括 idle 和 returning。available=False 时不能接新任务。任务 ID 不要求连续，下标不能代替 ID。动态观测不提供未释放任务和总任务数；env.done 只作为驱动的终止信号。

当前地图和未来的已承诺车辆路径是可知信息，未来订单不是可知信息。可以据此估计占用或拥堵，但不能直接查询未来订单。

## 输出动作及处理规则

policy 输出有序列表 [(vehicle_id, task_id), ...]，允许空列表。一次最多给每辆可接单车分配一个 pending 任务。提交順序也是规划优先顺序；想改变优先级时，改变列表顺序。

assign(pairs) 返回逐对反馈，例如：

```python
{'vehicle': 0, 'task_id': 10, 'accepted': True,
 'planned_delivery_end': 25}
```

或 accepted=False、reason='no_route_within_horizon'、failed_leg='pickup'/'delivery'/'return'。失败的一对不改变该车路线，也不锁定任务。该任务之后可交给别的车或在下一时刻重试。不能把请求当成已经执行成功。

重复车、重复任务、未知 ID、未释放任务或忙碌车辆属于非法输入，整批在任何规划前抛 ValueError。合法批次按列表顺序逐对规划，可以部分成功；对后面失败不回滚前面成功项。两种错误处理要区分。

advance(steps=1) 同步执行给定步数，不在中途自动调用策略。默认只推进1步，避免错过任务到达。不能超过 horizon。reset() 恢复同一个场景，reset(new_scenario) 切换场景。

## 结果字段和日志

feasible=True 表示所有任务已完成且所有车停回自己的停车位。未完成时 reason 为 unfinished 或 horizon_exhausted。算法异常、非法动作由驱动自行记录，不能忽略。

makespan 是最后一单卸货完成时刻；time 是实际执行截止时刻，成功场景包含最终返回。mean_flow_time 是已完成单的平均 (C−release)，只有成功场景可直接用于完整任务目标比较。

moves 是实际移动次数。service_steps、idle_steps、traffic_wait_steps 将静止的步分为服务、空闲、行驶阶段等待；所有步合计满足：

```text
moves + service_steps + idle_steps + traffic_wait_steps
    = 车辆数 × time
```

traffic_wait_steps 是“行驶阶段的停留”，并非严格因果归因的拥堵延误；名字不能用于直接证明拥堵导致了多少时间损失。

paths[k][t] 是实际执行轨迹，不包含尚未执行的未来。assignments 保存成功指派时的预约事件，包括计划 return_end；返程被后续任务替换时，这个历史 return_end 不再是该次实际回家时刻。events 只包含已完成任务，取送事件在锁定规则下保持有效。interval_states 是各步执行状态，用于展示；独立验证器重建服务时段检查指标，不依赖它来判断避碰。

## 匈牙利算法与 DQN 的接法

第三项接口更新：result新增max_flow_time、p90_flow_time、时间分解均值、empty_moves、loaded_moves、workload_cv、per_vehicle及task_metrics，原有字段保留。comparison_valid用于完整比较资格，metrics_scope表示是否只统计完成子集。具体口径和null处理见《评价指标说明.md》。未改变observe/assign/advance及任务执行规则；这些事后统计不作为在线观测输入。

先从 available 车辆及 pending 任务构造矩阵。代价可以是取货行驶估计＋载货行驶估计＋服务时间，并加入订单已等待时长及已知通道占用等项。匹配结果转为 pairs，明确未匹配和矩阵不可达项的处理。匈牙利算法保证当前给定代价矩阵上的最优匹配，不保证实际全程调度最优。

DQN 可以输出少量离散动作，例如选择3至5种固定代价权重，再调用匹配器。车辆数和 pending 数可变化，需要算法同学设计固定维度的状态汇总、动作含义和奖励。环境不预置某种奖励，避免把奖励设计误当成物理模型。

GA 若要规划完整静态任务队列，可以让策略按队列在车辆可接单时提交下一单。动态测试不能提前将完整未来任务队列交给在线策略。原先 agv_coursework 的离线整队列解码器与这里逐时指派的执行方式不同，旧成绩不可直接当作新环境基线。
